# 速く送る（速さ優先モード）の仕組みと、使えないカタログ

「速く送る」（旧称「速さ優先」）は、書き出しの代わりに、Lightroom Classic が持っているプレビュー画像を
`photo:requestJpegThumbnail(2048, 2048, callback)` で受け取って送る方式です（**1.1.0 から既定はオン**。ギャラリーを作る画面の
「この回だけ、書き出して送る」で、1回だけ書き出しにできます）。
カタログの状態によって、プレビューが無い・古い・カメラの JPEG のまま、ということがあるため、次のように守っています。

## 守り方（`lib/pipeline.lua`）

1. **最初に3枚（最初・真ん中・最後）を試し取りして、そのカタログでプレビューが使えるかを決める。**
   3枚中 2 枚以上が使えなければ、最初から全部を通常の書き出しで送る（途中で遅くなるのを避ける）
2. 1枚ごとに、使えなければその写真だけ通常の書き出しに回す。**失敗が3回続いたら、残りは書き出す**
3. プレビューが使えない理由（ログ `previewRejected=[…]`）
   - `none` 取得できなかった／`timeout` 10 秒待っても来なかった
   - `invalid` JPEG として読めない
   - `embedded` Exif・XMP・IPTC が付いている（= Lightroom が描画したプレビューではなく、カメラが埋め込んだ JPEG）
   - `large` 長辺 2560px 超（標準プレビューサイズが大きい、1:1 プレビューが返った、など）
   - `small` 長辺 1900px 未満
4. 送った枚数の内訳（プレビューから N 枚・書き出しで M 枚）を結果に出す。書き出しのほうが多いときは
   「標準サイズのプレビューを作っておくと速くなります」と一言添える
5. メタデータは、どちらの方法でも、取り除いたうえで著作権・作成者・連絡先だけを入れ直す（`docs/send-pipeline.md`）。動画は送らない

## 届く大きさ（標準プレビューサイズ）

観測（Lightroom Classic。2 台のカメラが混ざった 299 枚）: 標準プレビューサイズ「自動」＝ 4112px のカタログで、
届いた長辺は **2056px**（= 4112 の半分）。元画像の画素数とは無関係でした（カメラが違っても同じ 2056px）。
Lightroom は標準プレビューサイズを起点に、半分ずつの段階を持っていて、API は「要求（2048）以上でいちばん小さい段階」を
返す、と読めます（推測）。起点は、**設定値と元の画像の長辺（トリミング後）の小さいほう**です（観測: 長辺 3000px の画像は、
設定 4112px でも 3000px で作られ、その半分の 1500px では足りないため、3000px のまま届いた）。したがって、画素数の少ない
カメラの写真や、大きくトリミングした写真は、ほぼ元の大きさで届きます。選択肢は 自動／1024／1440／1680／2048／2880。

| 標準プレビューサイズ | 段階 | 返る長辺（予想） | プラグインの扱い |
|---|---|---|---|
| 1024・1440・1680 | 2048 に足りない | その場で描画される（2048px 前後の見込み。**未確認**）。時間は書き出しに近いはず | 試し取りの平均が 0.8 秒/枚以上なら、最初から書き出し |
| 2048 | 2048 | 2048px | そのまま使う |
| 自動 4112（MacBook Pro 16 の「スペースを拡大」の 2 倍） | 4112 / 2056 | 2056px（観測） | そのまま使う |
| 自動 5120（5K ディスプレイ） | 5120 / 2560 | 2560px（予想） | 使う（上限ちょうど） |
| 2880 | 2880 / 1440 | 2880px（予想。ファイルは約2倍） | 長辺 2560px 超なので書き出し |
| 自動 3840（4K ディスプレイ） | 3840 / 1920 | 3840px（予想） | 書き出し |

プラグインは、長辺 2560px を超える（例: 3000px の元画像）プレビューは書き出しに回します（Lightroom が 2048px にします）。
2560px を超えるものを書き出しにするのは、LP とプラグインの画面が「長辺 2048px」と説明しているためです。縮小する手段（デコード・
再エンコード）をプラグインは持たないので、大きいものは通さず、書き出し（Lightroom が 2048px にする）に回します。
2056px・2560px は、説明の 2048px に近いものとして通しています。

プレビュー画質（低・中・高）は、届く JPEG の画質と 1 枚のサイズに関わります（観測: 「中」で量子化表からの推定が 88 前後。
「低」「高」は**未確認**）。

## カタログの状態ごとの整理

「確かめた」は SDK・Adobe のヘルプ・コミュニティの記述、「推測」は書かれていないことからの推測です。
実機で確かめる手順は `docs/manual-test.md` の P 章にあります。

| 状態 | 確かめたこと | 推測・未確認 | プラグインの振る舞い |
|---|---|---|---|
| 標準プレビューがまだ無い | SDK: 要求したサイズのプレビューが無ければ、その場で**描画される**。要求サイズは最小値で、それ以上の最小のプレビューが返る | 待ち時間は書き出しと同程度。**描画が必要なときに callback が来ない**という報告がある（古い版・古い RAW 形式） | 試し取りで判定。10 秒で見切り、3 回続けて失敗したら書き出し |
| 読み込みが「埋め込みとサイドカー」 | Adobe: カメラの埋め込みプレビューは色管理されず、Lightroom の解釈と一致しない | API が埋め込み JPEG を返すかは**未確認**。返るなら現像が反映されない。描画済みのプレビューには Exif が無い（観測）ため、**Exif が付いていれば埋め込み**と見なせる | Exif／XMP／IPTC があれば `embedded` として書き出し |
| 現像を変えた直後（プレビューが古い） | コミュニティ: 「プレビューが最新なら API は作らない」（= 古ければ作る）という記述 | 古いまま返るかは**未確認**。検知する API は無い | 検知できない。**だから既定にはしない**。色・現像を見るクライアントには通常を勧める |
| 標準プレビューサイズが 2048 より小さい（1440・1680 など） | 要求(2048)以上のサイズが描画される（SDK） | 描画されず小さいまま返る場合は `small` として書き出す | `small`（1900px 未満）は書き出し |
| 標準プレビューサイズが大きい（2880、「自動」で画面が大きいとき） | 返るのは「要求以上で最小のもの」 | 2560px を超えると `large` で書き出す。LP は「長辺 2048px」と説明しているため、大きいまま送らない | `large` は書き出し |
| 元ファイルがオフライン（スマートプレビューのみ） | スマートプレビューは現像用の縮小 DNG で、ライブラリのプレビューとは別。オフラインでも、書き出しはスマートプレビューから行われる（大きさはスマートプレビュー以下に制限される）という説明がある | プレビュー取得（API）がどうなるかは**未確認** | 試し取りで判定。書き出しは Lightroom 任せ（サイズが 2048 に満たなければ、そのサイズで送られる） |
| 1:1 プレビューだけ／破棄される設定 | 1:1 は「1日／1週間／30日／なし」で破棄される。標準プレビューは通常残る。標準サイズが長辺の半分より大きいと、1:1 が標準として残る（Lightroom Queen） | 1:1 だけが返ると 2560px を超えて `large` になる | `large` は書き出し |
| 動画 | — | 「プレビュー」は静止画の1コマ | **送らない**（選択から除く。除いた本数を通知） |
| 仮想コピー・スタック・HDR／パノラマ | 仮想コピーは別の写真として自分の現像・プレビューを持つ | 結合結果（DNG）は通常の写真と同じと推測。**未確認** | 通常の写真と同じ扱い。同名ファイルは `-2` で区別する |

## 色について

**速さ優先で届く JPEG の画素は sRGB です。** 12 色の合成画像（3000×3000・sRGB）を Lightroom Classic に読み込み、
現像を触らずに送って、届いた各マスの値を測りました（有彩色 10 マスすべてが、元の sRGB の値と ±18 以内で一致。
Adobe RGB の数値なら大きく違うはずの値でした）。緑・シアンで赤チャンネルが 17〜18 になるのは、JPEG の色差の間引きによるもので、
写真では問題にならない範囲です。

- Adobe のヘルプは「標準プレビューは Adobe RGB」と説明していますが、API が返す画素は sRGB でした（以前の推測は誤りでした）
- JPEG には ICC プロファイルが付いていません。ブラウザは sRGB とみなすので、表示は正しい。ただし Photoshop など、
  タグなしを「作業用 RGB」とみなすソフトでは色がずれる恐れがあるため、プラグインは**書き出しと同じく sRGB のプロファイルを付けて**送ります
  （`lib/icc.lua`。公表されている sRGB の原色と階調曲線から生成。約 2.5KB。Apple の sRGB プロファイルと比べて、変換後の差は最大 4/255・平均 0.5/255）
- 「8 枚中 5 枚で、平均の明るさが 4〜7% 低い」は、色空間では説明できません。残る原因の候補: プレビューが現像の最新を反映していない、
  書き出し時の出力シャープの有無、プレビューと書き出しのトーン描画の差。調べる方法は `docs/manual-test.md` の P9

## 古いプレビュー（調査の結論）

1. **観測**: 同じ 5 枚で、10/11 の速さ優先だけが 3〜8% 暗く、標準プレビューを全削除して作り直したあとは通常の書き出しと一致した
   （通常の書き出しは 2 日とも同じ値。現像は変わっていない）。プレビューが現像の状態と合っていなかった、と読むのが自然
2. **資料**: SDK は鮮度について何も書いていない。コミュニティでは、Lightroom が「無効」と判定しなかったプレビューは古いまま返る
   （プラグイン作者 Rob Cole は「最新のプレビューを確実に得ることは解決できなかった」）。無効と判定されたものは描画される（遅い・まれに callback が来ない）
3. **見分け・更新**: プラグインからはできない。`lastEditTime`・`editCount`（写真の編集時刻）は取れるが、プレビュー側の時刻は無い。
   標準プレビューを作り直す API も無い（スマートプレビューだけ）。書き出しは常に最新
4. **方針（1.1.0）**: **速さ優先を既定にする**（運営者の決定 2026-10-14。296 枚で書き出し 約 8 分に対し、プレビュー 約 1.3 分）。
   古いプレビューの危険は、設定画面・README・ダイアログに明記し、ギャラリーを作る画面で「この回だけ、書き出して送る」を選べるようにする。
   「最近編集した写真は書き出す」は入れない（単純にする）。以前の記述（1.0.x の方針：既定にしない）は、下の「既定にしてよい条件」とあわせて、判断の経緯として残す
5. **任意の追加（保留）**: 直近に編集した写真（`lastEditTime` が新しいもの）だけ書き出す。効くのは直前の編集だけで、
   実際の流れ（編集してすぐ送る）では速さ優先の利点がほぼ消える。実機の確認手順は `docs/manual-test.md` の P3

## 既定にしてよい条件（1.0.x のとき。1.1.0 では、条件が満たされないまま、運営者の決定で既定にした）

1.0.x では、次がすべて満たされるまで、既定は通常の書き出しのままにする、としていた。1.1.0 では、未解決のまま既定をオンにしたので、
危険（古いプレビューが気づかれずに届く）は、画面の説明と「この回だけ書き出す」で補っている。

1. 明るさ: 「8 枚中 5 枚で 4〜7% 暗い」の原因を特定し、直す、または検知できるようにする（色の画素値は sRGB で一致している）
2. 古いプレビュー・埋め込みプレビューを、確実に検知できる（または、害がないことを示せる）
3. 試し取りが、実際のカタログ（読み込み直後・埋め込み設定・オフライン）で期待どおりに切り替わる
