# 送信パイプラインの設計

ギャラリーを作ったあと、写真をどう書き出し、送るか。実装は `papat.lrplugin/lib/pipeline.lua`、`lib/sender.lua`。

## 処理の流れ

```
設定ダイアログ → ギャラリー作成(API) → 【URL・パスコード・案内文をすぐ表示】
                                      └ 背景タスク（LrProgressScope・中断可）
   producer ─ 書き出し(or プレビュー) ─▶ queue(最大12) ─▶ worker ×3 ─ PUT photo ─▶ dirty ─ 3枚→10枚/10秒ごと ─▶ PUT manifest
                                                                                            └ 最後に complete=true
```

- 書き出しと送信を並行（レンダリングが終わった写真から送る）。キューは最大12枚で、メモリ・一時ファイルを抑える
- 送信は3並列（`pipeline.DEFAULT_CONCURRENCY`、最大4）。429 は `Retry-After` を待って再試行（最大5回）
- manifest は最初の3枚で1回目、以後10枚または10秒ごとに「新しい分だけ」を PUT（サーバーが source_id / stem で merge）。
  最後に `complete: true`。中断時も、送れた分で `complete: true` にする
- 計測: `書き出し`（producer の経過時間 ÷ 枚数）、`送信`（最初の送信〜最後の送信、1リクエストあたりの平均秒）、`全体`。
  ログ（`papat-lightroom.log` の `pipeline:` 行）と、完了ダイアログ／「最近のギャラリー」に出る
- 中断・再開: 未送信の写真（Lightroom の uuid と source_id）と、使用済みのファイル名を LrPrefs の `jobsJson` に保存。
  「最近のギャラリー」→「続きから送る」で、同じカタログから残りだけを送る（ファイル名が重複しないよう、既存名を避ける）
- 速さ優先: `photo:requestJpegThumbnail(2048, 2048)`。取れない写真は通常の書き出しに自動で切り替える


## メタデータ

画像に入れるのは、写真家が Lightroom に登録した「誰の写真か」だけにする。Lightroom が書き出したメタデータは信用せず、
いったんすべて取り除き（`lib/jpeg.lua`）、必要なものを、カタログの値から作り直して入れる（`lib/rights.lua`）。
通常の書き出しも、速さ優先（プレビュー）も、同じ経路。

| 入れる（Lightroom に登録されたもの） | 入れない |
|---|---|
| 著作権（Copyright）・著作権の状態・使用条件・著作権情報の URL | 位置情報（GPS・場所の名前） |
| 作成者（Creator）・肩書き | カメラ・レンズのシリアル番号 |
| 作成者の連絡先（住所・市区町村・都道府県・郵便番号・国・電話・メール・Web） | 現像設定（XMP-crs）・編集履歴・元の RAW のファイル名 |
| | 埋め込みサムネイル・撮影情報（機種・レンズ・露出など）・キーワード・タイトル・説明 |

- **書き込み先**: Exif の IFD0（Artist・Copyright。macOS のプレビュー・Explorer などが読む）と、XMP
  （`dc:rights`・`dc:creator`・`xmpRights:*`・`photoshop:AuthorsPosition`・`Iptc4xmpCore:CreatorContactInfo`。Photoshop・Bridge・InDesign が読む）
- **残す**: JFIF、ICC プロファイル（sRGB。プレビューには生成して付ける）、Adobe（APP14）の色変換情報
- **確認**: 初めて送るとき（入る内容が変わったとき）に、入る内容を見せて確認する。「入れずに送る」と、設定でのオフもできる。
  確認した内容のハッシュは LrPrefs に覚える（値そのものは保存しない）
- **書き換えの検証**（`lib/jpeg.lua`）: 次のすべてを確かめ、1 つでも外れたら、その写真は**送らない**（元のバイト列は送らない）
  1. 先頭が SOI（FF D8）、各セグメントの長さがファイル内に収まる、SOS（画像データの開始）がある
  2. 画像の寸法（SOF）が、書き換えの前後で同じ
  3. 終端に EOI（FF D9）がある（途中で切れたファイルは送らない）
  4. 書き換え後に、メタデータのマーカーが 1 つも残っていない
  5. **SOS の手前から終端までのバイト列が、元と 1 バイトも変わっていない**（セグメントの追加後にも確かめる）
- **失敗の扱い**: 通常の書き出し→その写真は「送れなかった写真」（再送・続きから送るの対象）。速さ優先→通常の書き出しに切り替える。
  足すセグメント（著作権・プロファイル）の組み立てだけが失敗したときは、検証済みの「メタデータなしの画像」を送る（元のバイト列は送らない）
- **ログ**: `pipeline images:` 行に、取り除いた種類ごとの数（`metadataRemoved=[…]`）と、入れ直した枚数（`rightsAdded=`）

## ギャラリーの並びと manifest の項目

- **並び順**: 撮影時刻の順 → 同じ時刻・時刻がない写真はファイル名順 → 最後に Lightroom での選択順。送信を始めるときに一度だけ決め、
  書き出し・送信・manifest の公開はこの順に進める。manifest には、先頭から連続して揃った分だけを載せる
  （どの写真のアップロードが先に終わるかには左右されない）。「続きから送る」は、残りを同じ規則で後ろに足す
- **`datetime`**: Lightroom が表示している撮影時刻（「撮影時刻を編集」で合わせた時刻 → 元の撮影時刻 → デジタル化時刻の順）を、
  カメラの時計のまま `YYYY-MM-DDTHH:MM:SS`（**ゾーンなし**）で入れる。ギャラリーは `slice(11,16)` で「時:分」を出し、
  `new Date(...)` で時刻の差を取るため、`Z` や `+09:00` を付けると表示がずれる。撮影時刻のない写真（スキャン・合成）は空
- **秒未満**: SDK では取れない。同じ秒の写真はファイル名順
- **`rating`**: Lightroom のレーティング（0〜5）。ギャラリーに「撮影者 ★★★」と表示され、「撮影者レーティング」で並べ替えられる
  （クライアントが付ける★とは別）。設定でオフにでき、そのとき 0。カタログの★は書き換えない
- **その他の項目**: `label` は空（カラーラベルは送らない）、`keywords` は空配列、`camera` は空、`group` は 0。
  `camera`（機種名）はギャラリーが表示も絞り込みもしておらず、入れる利点がないため入れない

## 送信の失敗の扱い

| 種類 | 例 | 扱い |
|---|---|---|
| 一時的 | 通信の失敗（タイムアウト・接続断）、HTTP 429・500・502・503・504、`temporarily_unavailable` | 1秒・3秒・9秒（±25% のばらつき）の間隔で最大3回やり直す。`Retry-After`（30秒まで）があれば、それより早くはやり直さない。それでも駄目な1枚は「送れなかった写真」にして、ほかの写真は続ける |
| 上限 | 413 `gallery_limit_reached` | 3秒ほど置いて1回だけ確かめ直す。同じ答えなら全体を止める。サーバーが現在値と上限を返せば、文言に出す |
| 全体を止める | 401（キー無効）、402 `card_required`・`monthly_limit`・`paid_country_blocked`、409 `billing_country_required`、403（`invite_only` ほか）、404・410（ギャラリーが終了・削除）、409 `gallery_closed` ほか | やり直しても変わらないため、すぐ止める。送れていない写真は残し、「続きから送る」で再開できる |
| 1枚だけの失敗 | 413 `file_too_large`、415、書き出し・メタデータ除去の失敗 | その1枚を「送れなかった写真」にして、ほかは続ける |

- 失敗が続くと並行数を 3 → 1 に下げ、5 枚連続で問題なく送れたら戻す
- 写真 6 枚が続けて送れなかったら、送信を一時停止して「サーバーが混み合っています。少し待って『続きから送る』を」と案内する
- ログに、やり直しの回数（`retries=`）、並行数の変更、最終的に失敗した写真の HTTP ステータスと code（`failedUploads=[500x1]`）を出す

## サーバーとの取り決め

プラグインが前提にしている、サーバー（papat 連携 API v1）側の挙動です。

1. **manifest は小さな単位で何度も送る**: 写真は届いた順に PUT し、manifest（`manifest.json`）は 3 枚、以後 10 枚または 10 秒ごとに
   「新しい分だけ」を PUT する。サーバーは `source_id`（なければ `stem`）で merge し、`count` を再計算する
2. **`complete`（boolean）**: 送信の途中の manifest は `complete: false`、最後の manifest は `complete: true`。
   ギャラリー画面はこれを見て、完了するまで manifest を取り直す（未知のキーなので、検証は通る）。
   Lightroom が送信の途中で終了した場合は `false` のまま残るが、「続きから送る」で完了にできる
3. **レート**: 3 並列で 1〜2 枚/秒、manifest は 10 枚ごと。429 は `Retry-After` を待って再試行する
4. **空のギャラリーを残さない**: 書き出しがすべて失敗した場合は、プラグインが `DELETE /api/v1/galleries/{sid}` で取り消す

## 更新のお知らせ

プラグインは `GET /api/v1/integration/status?client_id=papat-lrc&client_version=<版>` の `client` を使う。

| フィールド | 意味 | プラグインの扱い |
|---|---|---|
| `minimum_version` | これより古い版は使えない（床） | 手元の版 < minimum **かつ** minimum < latest のとき「必須」 |
| `latest_version` | 最新版 | 手元の版 < latest のとき「任意の更新」（1日1回まで通知） |
| `update_available` | 任意の更新がある | latest が無いときの補助 |
| `update_required` | 必須（明示） | true なら必ず「必須」 |

`minimum_version` と `latest_version` が同じ値で返ってきた場合は、新しい版の告知として扱い（任意の更新）、操作は止めません。
必須の更新にするには、`minimum_version` を最新版より小さい値にするか、`update_required: true` を返します。
通信できないとき、応答が読めないときは、何も表示せず、そのまま使えます。
